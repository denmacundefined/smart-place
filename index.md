# Smart Place — повна документація українською

**SMS ↔ REST IoT-шлюз на MikroTik LTE · GitHub Pages / Architect**

Smart Place перетворює звичайні SMS-команди на локальні HTTP-запити до IoT-пристроїв, повертає показники датчиків і надсилає автоматичні тривожні повідомлення. Для роботи користувачеві достатньо телефона зі звичайними SMS; хмарний сервіс і мобільний застосунок не потрібні. Цей README містить **усю документацію від А до Я**, без необхідності переходити до інших файлів.

**Підтверджено на реальному обладнанні:** MikroTik Chateau із RouterOS **7.24.6**, LTE-модем `lte1`, ESP32 `guard` за адресою `192.168.12.254`. Перевірено `help`, `get`, `set`, HTTP 200, SMS Scheduler, cron, газову тривогу (`alert=true`), доставку 4 з 4 SMS у контрольному тесті та повернення до `alert=false`. Окремий зафіксований збій — **`MBIM: MEMORY_FULL (6)`**; надійність безперервної доставки SMS **не гарантована** до окремого виправлення.

> **Межа поточної роботи.** Це документаційний реліз: RSC-код не змінюється. Виправлення SMS-пам'яті виконуватиметься тільки на наступному етапі за окремим рішенням. Це не сертифікована система пожежної, газової або промислової безпеки; потрібні незалежні апаратні захисти.

## 1. Загальний опис — для звичайного користувача


### 1.1. Що таке Smart Place

**Smart Place** — це невеликий SMS-шлюз на маршрутизаторі **MikroTik із LTE-модемом**. Він перекладає прості SMS-команди на запити до IoT-пристроїв у локальній мережі і, навпаки, перетворює відповіді пристроїв та сигнали тривоги на SMS.

Приклад: у будинку стоїть ESP32 з газовим датчиком, датчиками клімату й п'ятьма реле. Ви хочете дізнатися температуру або стан реле, коли немає домашнього інтернету. Надсилаєте SMS `get guard` на SIM у MikroTik і отримуєте значення датчиків. Коли газовий датчик піднімає прапорець тривоги, MikroTik може сам відправити повідомлення довіреним номерам.

#### Що дає в повсякденному використанні

1. **Віддалене читання стану** — показники температури, вологості, CO₂, тиску, газового сенсора та реле, якщо ці поля повертає конкретний ESP32.
2. **Керування підтримуваними функціями** — наприклад, відправлення JSON-масиву станів реле або пар `ключ значення`.
3. **Автоматичні SMS про тривогу** — якщо у відповіді ESP32 `"alert": true` і для цього пристрою увімкнено моніторинг.
4. **Роботу без сторонньої хмари** — маршрутизатор безпосередньо звертається до локальної IP-адреси пристрою через HTTP.
5. **Кілька IoT-пристроїв** — кожен новий пристрій додається окремим JSON-файлом, без зміни командного синтаксису шлюзу.
6. **Список довірених телефонів** — лише телефони з локального whitelist можуть виконувати команди, якщо список непорожній.

### 1.2. Чого проєкт не робить

- Не є мобільним застосунком, хмарною платформою чи VPN.
- Самостійно не вимірює газ, температуру чи стан реле — дані надає ESP32.
- Не має вебпанелі для налаштування або зберігання довгої історії вимірів.
- Не шифрує HTTP-трафік між MikroTik та ESP32: у поточній версії використовується `http://IP/`.
- Не гарантує доставку SMS: це залежить від SIM, модема, мережі оператора та пам'яті SMS.
- Не замінює сертифіковані системи газової/пожежної безпеки, фізичну сирену та автоматичне перекриття газу.
- Не здійснює автоматичного повторного виконання небезпечних команд `set` при помилках доставки.

### 1.3. Що потрібно для роботи

| Компонент | Для чого | Приклад у перевіреній системі |
|---|---|---|
| MikroTik з RouterOS v7 і SMS-сумісним LTE-модемом | Читає SMS, виконує скрипти, опитує пристрої | Chateau, RouterOS `7.24.6` |
| SIM з активними SMS | Канал команд та сповіщень | SIM у модемі `lte1` |
| Локальна IP-зв'язність | Доступ MikroTik до пристрою | HTTP до `192.168.12.254` |
| IoT-пристрій з REST/JSON | Датчики, реле, прапорець тривоги | ESP32 `guard` |
| Декілька файлів у `flash/` | Опис пристрою та дозволені номери | `smart-place-device-guard.json`, `smart-place-trusted-numbers.txt` |
| Інсталятор `.rsc` | Створює скрипти та Scheduler | `smart-place-install.rsc` |

**Важливо.** Інсталяція Smart Place **не встановлює прошивку ESP32** і не створює для нього REST API. Пристрій повинен уже відповідати узгодженим JSON-форматом.

### 1.4. Сценарії користування

#### Читання клімату і реле

Відправте `get guard`. Повертаються текстові рядки виду `Temperature 1 = 30.6`, `Humidity 1 = 35.1`, `Relay 1 = 1`. Значення **динамічні** й можуть відрізнятися від наведених.

#### Керування п'ятьма реле

Відправте `set guard [0,0,0,0,0]`. Шлюз сформує HTTP POST на ESP32. Команда змінює стан пристрою: застосовуйте її лише після перевірки, що вимикання реле не спричинить небезпеки.

#### Сповіщення про газ

ESP32 визначає умови тривоги та включає `"alert": true` у GET-відповіді. Smart Place помічає перехід стану й ставить подію в RAM-чергу. SMS Handler відправляє відповідь усім довіреним номерам. Після повернення `alert=false` стан вважається скинутим. У реальному тесті 15.11.2026 були отримані всі **4 частини** повідомлення про газову тривогу.

### 1.5. Що вже перевірено

| Перевірка | Фактичний результат | Коментар |
|---|---|---|
| Парсинг JSON-файлу `guard` | Так | У self-test та ручному діагностичному тесті |
| Локальний HTTP GET | Так, `200 OK` | Читання датчиків працює |
| Перетворення JSON на SMS | Так | Довгі відповіді розбиваються на частини |
| `help guard` | Так | Є ручне й автоматичне отримання відповіді |
| `set guard` | HTTP POST дав повідомлення `status success` | Незалежна перевірка **кожної** зміни реле в цьому тесті не задокументована |
| Cron через Scheduler | Так | `run-count` зростав, нових warnings не було |
| Права Scheduler із `sensitive` | Так | Без нього читання `contents` давало `nil` |
| Автоматична газова тривога | Так, 4/4 SMS | Перевірено на реальному датчику |
| Скидання `alert=false` | Так | Повернення до норми підтверджено |
| Повторне спрацювання після скидання | Немає окремого контрольного тесту | Потрібна безпечна програмна імітація |
| Повна перевірка whitelist з кількох номерів | Ні | Окремий тест ще потрібен |
| Безперервна надійність SMS | Ні | Є відома помилка `MBIM: MEMORY_FULL` |

### 1.6. Обмеження масштабу

Шлюз **динамічно** виявляє файли `flash/smart-place-device-*.json`. Кількість пристроїв не зафіксована жорстко, але вони опитуються послідовно в одному скрипті. З кожним новим пристроєм збільшується тривалість обходу, використання оперативної пам'яті й навантаження на маршрутизатор/мережу. Для десятків пристроїв потрібне окреме тестування продуктивності.

### 1.7. Короткі відповіді на запитання

**Чи потрібен інтернет на MikroTik?** Для локального HTTP GET — ні, якщо є маршрут до ESP32. Для SMS потрібна активна послуга SMS та робота модема в мережі. Інтернет через LTE може бути корисним, але сама SMS-логіка не звертається до хмарного сервера.

**Чи можна додати ще один ESP32?** Так, якщо він має сумісний HTTP/JSON-інтерфейс. Додайте файл `flash/smart-place-device-<ім'я>.json`. Деталі — в [конфігурації](#configuration).

**Чи переживе перезавантаження?** Скрипти та конфіги зберігаються; оперативні стани й черги — ні. Див. [експлуатацію](#operations).

**Чи захищено доступ?** Лише в межах whitelist телефонних номерів і контролю мережі; SMS не є криптографічною автентифікацією. Див. [безпеку](#security).

## 2. Архітектура Smart Place


### 2.1. Ідея архітектури

Smart Place — це **два незалежні скрипти RouterOS**: один працює з SMS, інший із пристроями. Конфігурації пристроїв зберігаються у `flash/`, а тимчасові стани, останні перевірки та черга тривог — у RAM. Фізичний LTE-модем використовується для надсилання SMS **лише одним скриптом** — `smart-place-sms-handler`.

![Схема компонентів Smart Place із розділенням SMS і фонових алертів](assets/architecture.svg)

**Легенда.** Суцільні стрілки — SMS або HTTP-запити; пунктирні — конфігурація/керування/черга. Вихідні коди діаграм: [компонентна схема](diagrams/components.mmd) і [UML-варіант](diagrams/components.puml).

### 2.2. Фізичні та програмні компоненти

| Компонент | Функція | Де живе | Стан / надійність |
|---|---|---|---|
| Телефон користувача | Надсилає `help/get/set`, отримує SMS | Мобільна мережа | Поза контролем шлюзу |
| LTE SIM + модем `lte1` | SMS-канал між телефоном і роутером | MikroTik | Можлива помилка `MEMORY_FULL` |
| RouterOS `/tool sms inbox` | Приймає вхідні повідомлення | Модем/RouterOS | Старі SMS можуть залишатися через помилки видалення |
| `smart-place-sms-handler` | Валідація номера, команди, HTTP, розбивка й надсилання SMS | `/system script` | Один екземпляр за раз; пауза 3 с між частинами |
| `smart-place-cron` | Опитування JSON-пристроїв і визначення переходів тривоги | `/system script` | Один екземпляр; послідовний обхід |
| `smart-place-sms-tick` | Запуск SMS Handler кожні 20 с | `/system scheduler` | Початково вимкнений |
| `smart-place-alert-tick` | Запуск cron кожні 20 с | `/system scheduler` | Початково вимкнений |
| `spPendingAlerts` | RAM-черга повідомлень про тривогу | Глобальна змінна RouterOS | Зникає після перезапуску/імпорту |
| `spLastCheck`, `spPriorAlert` | Час опитування і попередній `alert` | Глобальні змінні RouterOS | Зникають після перезапуску/імпорту |
| `spHandledSms` | RAM-ідентифікатори оброблених SMS | Глобальна змінна RouterOS | Не переживає перезапуск/імпорт |
| `flash/smart-place-device-*.json` | Конфігурації пристроїв | Постійна пам'ять MikroTik | Не змінюються інсталятором |
| `flash/smart-place-trusted-numbers.txt` | Довірені номери | Постійна пам'ять MikroTik | Не змінюється інсталятором |
| ESP32 `guard` | Віддає показники / приймає JSON-POST | `192.168.12.254` | Працює окремо від RouterOS |

### 2.3. Послідовність виконання `get guard`

![Послідовність SMS → Handler → HTTP GET → SMS](assets/sms-sequence.svg)

1. Телефон надсилає SMS `get guard` на SIM у MikroTik.
2. `/tool sms` приймає SMS у Inbox; **не** потрібно вмикати виконання RouterOS-команд із SMS за його вбудованим синтаксисом `:cmd`.
3. `smart-place-sms-tick` викликає `/system script run smart-place-sms-handler` (планувальник — кожні 20 с).
4. Handler відкидає невалідних відправників, перевіряє whitelist і впізнає `get`, `set`, `help`.
5. Для `guard` шукає **рівно один** файл `flash/smart-place-device-guard.json` і розбирає його як JSON.
6. Виконує `GET http://192.168.12.254/` через RouterOS `/tool fetch output=file dst-path=smart-place-sms-http.txt` — тимчасовий **RAM-файл**, після зчитування видаляється.
7. При `get=flat` перетворює JSON-поля на `ключ = значення`; при `get=raw` залишає текст відповіді.
8. Ділить рядок на окремі короткі SMS (64 символи даних на частину; до 8 частин, далі обрізання з `[TRUNCATED]`), додає заголовок `guard 1/4: ...`.
9. Відправляє частини в `lte1` із паузою **3 секунди** між викликами, записує збій конкретної частини до журналу. Автоматичний повтор SMS відсутній.
10. Помічає SMS як оброблену в RAM та намагається видалити її з Inbox; при помилці видалення наступний запуск не має повторно виконати її до скидання RAM-стану.

`help guard` відрізняється: повертає поле `help` **із локального конфігураційного файлу** без HTTP GET. Для `set guard ...` виконується POST із JSON-тілом.

### 2.4. Послідовність аварійного сповіщення

![Схема автомата станів тривоги — FALSE, TRUE, черга і скидання](assets/alert-state.svg)

1. `smart-place-alert-tick` запускає `smart-place-cron` **кожні 20 с**.
2. Cron шукає всі `flash/smart-place-device-*.json` та для кожного перевіряє `"alert": true` у **конфігурації** (це перемикач *моніторингу*, не ознака аварії).
3. Для пристроїв із дозволеним моніторингом порівнює `spLastCheck[device]` з поточним часом. При `interval=60` він має опитувати пристрій орієнтовно кожні **60 с**, а не кожні 20 с.
4. Робить HTTP GET до кореневого `http://IP/` і розбирає JSON.
5. Якщо **JSON-відповідь пристрою** містить `"alert": true`, а попередньо `spPriorAlert[device]` не був `true`, формується звіт і записується до RAM-черги `spPendingAlerts[device]`.
6. **Cron не виконує `/tool sms send`.** На наступному циклі `smart-place-sms-handler` забирає чергу й надсилає повідомлення **кожному номеру у trusted list**. У публічному режимі (порожній whitelist) немає одержувачів алертів.
7. Коли пристрій знову повідомляє `"alert": false`, cron скидає `spPriorAlert[device]=false`. Це дозволяє сформувати нове сповіщення при наступному переході в `true`.

**Семантика:** це сповіщення про *перехід* у стан тривоги, а не періодична розсилка кожні 60 с. Не варто очікувати повідомлення при кожному опитуванні, поки `alert=true`.

### 2.5. Рівні конфігурації та стани

#### Постійна конфігурація

```text
flash/
├── smart-place-device-guard.json
├── smart-place-device-<other>.json
└── smart-place-trusted-numbers.txt
```

Дані файли повинні зберігатися у `flash/` (на протестованому Chateau це постійна пам'ять). Встановлення не переписує їх. Права виконання Scheduler **повинні містити `sensitive`**: без цього на перевіреній системі `/file get ... contents` повертав `nil` замість рядка.

#### Тимчасові дані в RAM

```text
spLastCheck[device]     = час останнього GET
spPriorAlert[device]    = true / false
spPendingAlerts[device] = текст звіту (не черга з необмеженою історією)
spHandledSms[id]        = true, доки RAM-стан збережений
smart-place-sms-http.txt   (тимчасовий результат GET/POST)
smart-place-cron-http.txt  (тимчасовий результат GET)
smart-place-selftest-http.txt (тимчасовий результат GET)
```

Ці файли **не повинні опинятися в `flash/`**: у поточному коді вони створюються у корені Files, який на перевіреному обладнанні використовував RAM. Із втратою RAM-стану сповіщення в черзі зникає; якщо `alert=true` все ще активний, може бути сформований повторний алерт після наступного опитування.

### 2.6. Формат HTTP API

На поточному `guard` адреса GET і POST однакова:

```http
GET http://192.168.12.254/
```

GET має повертати JSON-об'єкт, який включає `"alert": true` або `false` для фонового контролю. Інші ключі (наприклад `"CO2"`, `"Relay 1"`) передаються користувачеві як є: **назви полів задає ESP32, не RouterOS**.

```http
POST http://192.168.12.254/
Content-Type: application/json

[0,0,0,0,0]
```

POST для `set guard d 2 r 4` надсилає об'єкт `{"d":2,"r":4}`. Сервер ESP32 визначає, які дані допустимі і що змінюється від POST. Докладніше — [API та налаштування](#configuration).

### 2.7. Два Scheduler — два різні інтервали

| Механізм | Приклад | Що він означає |
|---|---|---|
| `smart-place-sms-tick interval=20s` | 20 секунд | Як часто перевіряти Inbox і відправляти RAM-чергу |
| `smart-place-alert-tick interval=20s` | 20 секунд | Як часто cron перевіряє, **чи настав час** для кожного пристрою |
| JSON пристрою `"interval":60` | 60 секунд | Мінімальний бажаний інтервал GET для цього пристрою |

Не плутайте `run-count` Scheduler із кількістю HTTP-запитів. Лічильник збільшується кожні 20 с, а GET для `guard` виконуватиметься рідше.

### 2.8. Ізоляція процесів і межі надійності

Розділення зменшує конфлікти за LTE-модем: cron ніколи не надсилає SMS, тому `help guard` не змушений чекати завершення обходу всіх датчиків. Але є важливі обмеження:

- **Немає постійної черги подій.** `spPendingAlerts` — асоціативний масив у RAM; новий запис із тим самим ім'ям перезаписує старий звіт.
- **Черга скидається SMS Handler до відправлення.** При `MBIM: MEMORY_FULL` невідправлений алерт не буде гарантовано повторений; відсутній механізм гарантованої доставки/acknowledgement.
- **Можливий застарілий алерт.** Якщо тривога скинулася раніше, ніж SMS Handler забрав подію, queued-сповіщення все одно може бути відправлене.
- **Може бути повтор після reboot/import.** `spPriorAlert` і `spHandledSms` втрачаються; старі SMS у Inbox можуть знову стати кандидатами для обробки.
- **SMS не є криптографічно довіреним транспортом.** Для критичних виконавчих пристроїв потрібні додаткові бар'єри.

## 3. Встановлення на чистий MikroTik із LTE — від А до Я


**Мета:** із чистого або раніше не налаштованого RouterOS отримати стабільно запущені SMS-команди `help/get/set` і фонове опитування `guard`. Усі дії поділено на етапи: **не активуйте автоматику до успішного ручного тесту**.

**Опрацьована платформа:** MikroTik Chateau / RouterOS **7.24.6** / LTE **`lte1`** / ESP32 **`192.168.12.254`** / SMS-порт `lte1`. На інших моделях назви інтерфейсів, підтримка SMS, схема дисків і синтаксис окремих команд можуть відрізнятися: спочатку перевірте сумісність.

### 3.1. Карта встановлення

| Етап | Що робимо | Критерій готовності |
|---|---|---|
| 0 | Резервна копія RouterOS та підготовка обладнання | Маємо доступ через WinBox/SSH і план відновлення |
| 1 | SIM, LTE, перевірка SMS | Модем видимий; `/tool sms` показує `status: running` |
| 2 | Локальна мережа до ESP32 | `ping` і HTTP GET проходять |
| 3 | `flash/` та JSON-файли | Один коректний `guard.json` + **непорожній** whitelist |
| 4 | Завантаження RSC і синтаксична перевірка | `/import ... dry-run` без помилок |
| 5 | Імпорт | 3 скрипти, 2 вимкнені Scheduler |
| 6 | Self-test / ручний SMS / cron | HTTP 200; `help/get` відпрацьовують |
| 7 | Cron Scheduler | Лічильник росте, нових warnings немає |
| 8 | SMS Scheduler | `help guard` відпрацьовує без ручного запуску |
| 9 | Функціональний тест тривоги | Реальний перехід `false→true→false`, SMS приходять |
| 10 | Захист і обслуговування | Whitelist, бекап, нагляд за модемом |

### 3.2. Етап 0 — підготовка та безпека

1. Забезпечте **живлення** MikroTik і ESP32, SIM з послугою SMS та доступ до локальної мережі.
2. Підключіться через WinBox або SSH **із власної довіреної мережі**. Не відкривайте WinBox/SSH у загальний інтернет.
3. Переконайтеся, що ви маєте адміністративні права; Smart Place потребує `ftp,read,write,test,policy`, а його **Scheduler** додатково `sensitive`.
4. Збережіть резервну конфігурацію маршрутизатора згідно з правилами вашої мережі. Для чистого тестового пристрою можна додатково виконати:

   ```routeros
   /system backup save name=before-smart-place
   /export file=before-smart-place-export
   ```

   Резервна копія може містити секрети. Скопіюйте її у захищене місце, **не завантажуйте в публічний GitHub**; не залишайте великі резервні файли на роутері з мінімальною вільною flash-пам'яттю.

5. **Не запускайте `/system reset-configuration`** лише заради Smart Place. Встановлення не потребує скидання роутера до заводського стану.

### 3.3. Етап 1 — налаштування SIM і LTE

#### 3.3.1. Підключення модема

Установіть активну SIM у маршрутизатор (живлення/встановлення SIM — згідно з інструкцією конкретної моделі). Перевірте, як називається LTE-інтерфейс:

```routeros
/interface lte print detail
/interface lte monitor lte1 once
```

На перевіреному Chateau модем — `lte1`. Якщо у вас інший інтерфейс, **перед імпортом адаптуйте значення** `smsPort "lte1"` у RSC; не міняйте вхідні параметри довільно. APN за потреби налаштовується в конфігурації LTE оператора — Smart Place сам APN не змінює:

```routeros
/interface lte apn print
```

Для локального REST-запиту доступ до інтернету через LTE **не обов'язковий**: MikroTik і ESP32 повинні мати локальну IP-зв'язність. Але SIM має працювати в мобільній мережі для надсилання й приймання SMS.

#### 3.3.2. Увімкніть приймання SMS

```routeros
/tool sms set port=lte1 receive-enabled=yes
/tool sms print
```

На протестованому пристрої `status: running`, `receive-enabled: yes`, `port: lte1`. Якщо ні, перевірте SIM, модем, налаштування SMS і підтримку конкретної моделі. У деяких конфігураціях може бути корисним `polling=yes` (RouterOS v7.16+), але **вмикайте лише якщо необхідно** й підтримує ваш модем.

> Smart Place читає звичайні текстові повідомлення з `/tool sms inbox`. Не потрібно надсилати вбудовану RouterOS-команду `:cmd ...`, а також не потрібно вмикати дистанційне виконання адміністративних скриптів через SMS.

#### 3.3.3. Тест приймання й відправлення

Надішліть **звичайну SMS** з власного телефона на номер SIM у MikroTik, наприклад `test`, потім:

```routeros
/tool sms inbox print detail
```

Повідомлення має бути у Inbox (надалі Smart Place його не оброблятиме, бо це не підтримувана команда). Для тесту вихідної SMS можете використати **свій номер**, підставивши його замість шаблону:

```routeros
/tool sms send port=lte1 phone-number="+380XXXXXXXXX" message="SP modem test" status-report-request=no
```

Шаблон `+380XXXXXXXXX` **потрібно замінити**, його не слід надсилати буквально. Кожна SMS може тарифікуватися. Якщо модем повертає `MBIM: MEMORY_FULL`, діагностику пам'яті залишаємо на **окремий етап** — тут нічого не чистимо навмання.

### 3.4. Етап 2 — мережа до ESP32

ESP32 із REST-інтерфейсом повинен бути доступний маршрутизатору по IP. Для `guard`:

```routeros
/ping 192.168.12.254 count=4
/ip address print
/ip route print
```

Якщо ESP32 у іншому VLAN/підмережі, налаштуйте маршрути та правила firewall відповідно до вашої мережі. **Не переналаштовуйте bridge/LAN наосліп**: на реальному маршрутизаторі це може від'єднати WinBox, DHCP та інші пристрої. Адреса `192.168.12.254` — фактична IP-адреса тестового `guard`, а не IP за замовчуванням будь-якого MikroTik.

Опціонально перевірте HTTP до ESP32 без відправлення SMS:

```routeros
/tool fetch url="http://192.168.12.254/" http-method=get output=file dst-path=sp-install-probe.txt
/file print where name="sp-install-probe.txt"
```

Після перевірки **приберіть лише тестовий RAM-файл**:

```routeros
/file remove [find name="sp-install-probe.txt"]
```

Якщо GET повертає не JSON або HTTP-помилку, спочатку виправте ESP32/мережу. **Інсталятор не створює REST API на пристрої.**

### 3.5. Етап 3 — підготовка файлів `flash/`

#### 3.5.1. Перевірте постійний диск

```routeros
/file print
/system resource print
```

На перевіреному Chateau папка `flash/` була доступна, а вільного місця у внутрішньому сховищі було дуже мало. Зберігайте там **лише малі постійні конфіги**, а результати `fetch` не переносьте з RAM до `flash/`.

Якщо `flash/` **відсутня**, ця збірка **не підтримує автоматично іншу схему зберігання**: потрібно адаптувати шляхи `flash/...` у скриптах і перевірити поведінку при перезавантаженні. Для документованого встановлення потрібна справжня папка `flash/`.

#### 3.5.2. Файл пристрою `guard`

У текстовому редакторі на комп'ютері створіть **UTF-8 без BOM** файл `smart-place-device-guard.json`:

```json
{
  "name": "guard",
  "ip": "192.168.12.254",
  "alert": true,
  "interval": 60,
  "help": "Guard: get guard | set guard [1,0,0,1,0]",
  "get": "flat",
  "set": "auto",
  "wrap": ""
}
```

Той самий файл як шаблон: [завантажити `guard.json`](downloads/smart-place-device-guard.example.json). За допомогою WinBox → **Files** завантажте файл **всередину `flash/`**, не в корінь. Назва у `flash/` має бути **точно** `smart-place-device-guard.json`.

Перевірте:

```routeros
/file print detail where name="flash/smart-place-device-guard.json"
:put [/file get [find name="flash/smart-place-device-guard.json"] contents]
```

Має виводитися текст JSON; у файлі не повинно бути `//`-коментарів, випадкових символів чи невидимих префіксів.

#### 3.5.3. Файл довірених телефонів

Створіть файл **з точною назвою** `smart-place-trusted-numbers.txt`, помістіть його в `flash/`. Вміст (це **приклад із плейсхолдерами**, замініть на свої номери):

```text
+380XXXXXXXXX
+372XXXXXXXX
```

Один номер у міжнародному форматі `+` і **лише цифри** на рядок. Без лапок, пробілів, коментарів і заголовків. Рекомендовано UTF-8 без BOM, без порожніх рядків усередині; звичайний кінцевий перевід рядка допустимий. **Не публікуйте цей реальний файл на GitHub.**

Перевірте:

```routeros
/file print detail where name="flash/smart-place-trusted-numbers.txt"
:put [/file get [find name="flash/smart-place-trusted-numbers.txt"] contents]
```

**Критично.** У поточній реалізації **порожній** файл означає *публічний режим*: будь-який валідний міжнародний номер може надсилати `get`, `set` та `help`; автоматичні алерти не мають одержувачів. Відсутній або неправильно заповнений файл викликає блокування команд (`DENY ALL`). Для реальної експлуатації whitelist має бути **непорожнім і валідним**.

### 3.6. Етап 4 — завантажте RSC та перевірте синтаксис

[Завантажити останній зафіксований інсталятор](downloads/smart-place-install.rsc). Через WinBox → Files покладіть `smart-place-install.rsc` **у корінь Files**, не у `flash/`:

```text
Files/
├── smart-place-install.rsc       # інсталятор (корінь)
└── flash/
    ├── smart-place-device-guard.json
    └── smart-place-trusted-numbers.txt
```

У терміналі:

```routeros
/import file-name=smart-place-install.rsc verbose=yes dry-run
```

Упевніться, що немає помилок синтаксису/політик. Якщо встановлюєте поверх старої версії, **спочатку** вимкніть Scheduler і перевірте Inbox на старі `set`-команди. Повторний імпорт скидає RAM-ознаки оброблених SMS, тому невидалений `set` може виконатися ще раз. Див. [експлуатацію](#operations).

### 3.7. Етап 5 — імпорт інсталятора

```routeros
/import file-name=smart-place-install.rsc
```

Після успішного імпорту мають існувати **три скрипти** і **два Scheduler**:

```routeros
/system script print where name~"smart-place"
/system scheduler print detail where name~"smart-place"
```

Скрипти: `smart-place-selftest`, `smart-place-sms-handler`, `smart-place-cron`. Scheduler: `smart-place-sms-tick` і `smart-place-alert-tick`.

В обох Scheduler має бути `disabled=yes` і політика:

```text
ftp,read,write,policy,test,sensitive
```

Цей `sensitive` **обов'язковий** у підтвердженій конфігурації: без нього Scheduler знаходив файл у `flash/`, але отримував `type=nil bytes=0` при читанні `contents`. Проєкт навмисно **не запускає автоматику одразу після імпорту**.

### 3.8. Етап 6 — self-test і ручні функції

#### JSON + HTTP GET без зміни стану

```routeros
/system script run smart-place-selftest
```

Перевірте рядки:

```text
Worker config loader: OK (... bytes)
Cron config loader: OK (... bytes)
name=guard ip=192.168.12.254
HTTP transport: RAM file (output=file, no as-value, no keep-result)
status: finished
code: 200
... перелік показників ...
Self-test finished
```

Назва `Worker config loader` у self-test історична; окремий старий `smart-place-worker` більше не використовується. Self-test **не надсилає SMS і не виконує POST**. Він перевіряє `guard`, а не кожен доданий у майбутньому пристрій.

#### Ручний тест SMS-команди

Надішліть SMS **з номера, внесеного до whitelist**:

```text
help guard
```

Потім вручну запустіть Handler:

```routeros
/system script run smart-place-sms-handler
/system script job print detail
```

Очікується SMS-відповідь із вмісту `help` і відсутність завислого Handler. Якщо після виконання в терміналі з'являється `1`, це може бути результатом службового `print count-only`, а не код помилки.

Наступним тестом надішліть `get guard` і повторіть ручний запуск Handler. Очікується одна або кілька SMS з показниками (для перевіреного прикладу зазвичай **4 частини**, але довжина відповіді динамічна). Перевірте журнал, особливо `SMS part ... failed`.

#### Ручний тест cron

```routeros
/system script run smart-place-cron
/log print where message~"SmartPlace: cron failure"
```

Cron повинен виконатися без свіжих помилок. При `alert=false` автоматична тривога не формується. Під час **ручного** запуску `cron` SMS не надсилає.

#### SET — лише після перевірки безпеки реле

```text
set guard [0,0,0,0,0]
```

Це справжній **HTTP POST**, який може перемкнути виконавчі пристрої. Не перевіряйте його на небезпечному навантаженні. Якщо відповідь SMS загубилася, **не повторюйте команду без перевірки фактичного стану**.

### 3.9. Етап 7 — ввімкніть автоматичний cron

```routeros
/system scheduler enable [find name="smart-place-alert-tick"]
/system scheduler print detail where name="smart-place-alert-tick"
```

Очікується зростання `run-count` кожні 20 с. `interval=60` у JSON пристрою регулює частоту **HTTP GET**, а не частоту запуску Scheduler. Перегляньте **нові** помилки:

```routeros
/log print where message~"SmartPlace: cron failure"
/log print where topics~"script,warning"
```

Якщо нових `Empty device config` немає, це позитивна ознака. Для `guard` було підтверджено зміну `run-count` з 5 до 8 без нових warnings після додавання `sensitive`.

### 3.10. Етап 8 — автоматизуйте SMS-команди

Після перевірки whitelist і ручного Handler:

```routeros
/system scheduler enable [find name="smart-place-sms-tick"]
/system scheduler print detail where name="smart-place-sms-tick"
```

Надішліть **нову** SMS `help guard` і **не запускайте Handler вручну**. Відповідь має прийти автоматично. Після цього перевірте `get guard`; при довгій відповіді уважно перевірте всі частини.

> **Увага:** на тестовому обладнанні раніше виникала `MBIM: MEMORY_FULL (6)`. Навіть якщо конкретна SMS надійшла, доставка тривог не є гарантованою. Не використовуйте SMS як єдину систему захисту життя/майна.

### 3.11. Етап 9 — перевірка тривоги

Переконайтеся, що `"alert": true` у конфігурації **дозволяє опитування**, а **фактична GET-відповідь ESP32** може переходити `false→true→false`.

Безпечніший тест — програмна імітація на стороні ESP32, **без випускання газу**. Під час тесту переконайтеся, що при першому `true` прийшло SMS, при тривалому `true` немає повтора, після `false` стан скинуто. Реальний газовий тест на цій інсталяції вже був проведений користувачем: доставлено **4/4 SMS**, а скидання до `false` підтверджене. Але систематична повторна тривога після скидання й гарантії доставки ще не перевірені.

### 3.12. Етап 10 — завершення та приймання

Перевірте кінцевий стан:

```routeros
/tool sms print
/system script print where name~"smart-place"
/system scheduler print detail where name~"smart-place"
/system script job print detail
/log print where message~"SmartPlace:"
```

Контрольний список:

- [ ] LTE-модем у мережі, SMS працюють.
- [ ] ESP32 доступний за IP, GET повертає HTTP 200.
- [ ] У `flash/` є валідний JSON пристрою й **непорожній** whitelist.
- [ ] Рівно 3 актуальні скрипти та 2 Scheduler Smart Place.
- [ ] У **обох** Scheduler є `sensitive`; `run-count` зростає.
- [ ] Self-test без помилок; `help/get` приймаються тільки з довірених номерів.
- [ ] Немає нових `cron failure` / `Empty device config`.
- [ ] Відомий ризик `MEMORY_FULL` прийнятий як **незакритий**, алерти не вважаються гарантованими.
- [ ] Є локальні резервні копії та записана робоча версія RSC.

### 3.13. Якщо щось пішло не так

**Швидко зупинити обидва цикли без видалення файлів:**

```routeros
/system scheduler disable [find name="smart-place-alert-tick"]
/system scheduler disable [find name="smart-place-sms-tick"]
```

**Перевірити активні jobs:**

```routeros
/system script job print detail
```

**Не очищайте весь SMS Inbox автоматично** і не скидайте модем, доки не зрозумієте, які повідомлення в ньому зберігаються. Подальші інструкції — [Діагностика](#troubleshooting) та [Операції/оновлення](#operations).

## 4. Як користуватися Smart Place


Цей розділ написаний для користувача, який **не адмініструє MikroTik**. Потрібен лише телефон, номер SIM-картки у роутері й дозвіл на керування.

### 4.1. Як відправляти команди

Відкрийте стандартний застосунок SMS на телефоні, оберіть номер **SIM, що знаходиться в MikroTik**, і введіть одну команду **латиницею**. Команди в поточній версії чутливі до написання: користуйтеся саме малими літерами `help`, `get`, `set`. Ім'я пристрою — як у його JSON (для прикладу `guard`).

| SMS | Дія | Безпека |
|---|---|---|
| `help guard` | Отримати коротку підказку з конфігурації | Без змін стану |
| `get guard` | Прочитати датчики й реле через HTTP GET | Без змін стану |
| `set guard [0,0,0,0,0]` | Передати масив станів п'яти реле | **Може змінити реле** |
| `set guard d 2 r 4` | Передати JSON-об'єкт `{"d":2,"r":4}` | **Може змінити пристрій** |
| `set guard {"mode":1}` | Передати готовий JSON-об'єкт (якщо пристрій підтримує) | **Може змінити пристрій** |

Текст `guard` — це **коротке ім'я конкретного пристрою**, не марка RouterOS. Для інших конфігурацій імена можуть бути іншими.

### 4.2. Команда HELP

**Надішліть:**

```text
help guard
```

**Приклад відповіді:**

```text
Guard: get guard | set guard [1,0,0,1,0]
```

Текст підказки зберігається в `"help"` файлу `flash/smart-place-device-guard.json`. ESP32 при виконанні `help` не опитується — тому HELP може працювати, навіть якщо пристрій тимчасово недоступний.

### 4.3. Команда GET

**Надішліть:**

```text
get guard
```

**Приклад** (числа наведено з реального self-test, не як прогноз):

```text
CO2 = 605
Display index = 1
Gas (MQ9) = 29
Humidity 1 = 35.1
Humidity Comp = 36.1
Pressure = 100375
Relay 1 = 1
Relay 2 = 1
Relay 3 = 0
Relay 4 = 0
Relay 5 = 1
Temperature 1 = 30.6
Temperature 2 = 31.6
alert = false
```

Шлюз розділяє довгу відповідь на **кілька окремих SMS** із заголовками на кшталт:

```text
guard 1/4: CO2 = 605 ...
guard 2/4: ...
guard 3/4: ...
guard 4/4: alert = false
```

Кількість частин залежить від фактичного JSON. Якщо замість `4/4` отримали лише `3/4`, це **не обов'язково проблема ESP32**: перегляньте журнал модема. У перевіреній системі одна частина не надійшла через `MBIM: MEMORY_FULL`.

Зараз у коді максимум **8 частин**, ширина **64 символи даних** на частину. Надмірно довга відповідь обрізається з позначкою `[TRUNCATED]`. Це **окремі SMS**, а не операторське довге «склеєне» повідомлення.

### 4.4. Команда SET — керування пристроєм

**Увага: SET — реальна команда керування.** Не тестуйте її на нагрівачах, замках, насосах, газових клапанах, електричних контакторах або інших небезпечних навантаженнях без локального захисту.

#### Варіант A. Масив JSON

```text
set guard [0,0,0,0,0]
```

Після `set` Handler надсилає HTTP POST із тілом:

```json
[0,0,0,0,0]
```

Конкретний сенс `0/1`, відповідність порядку реле і допустимі переходи **визначає прошивка ESP32**. Smart Place не знає, що саме підключено до кожного реле, і не встановлює апаратних захистів.

#### Варіант B. Параметри ключ—значення

```text
set guard d 2 r 4
```

Тіло HTTP POST:

```json
{"d":2,"r":4}
```

Ключі можуть містити англійські літери, цифри, `_` і `-`; після них ідуть значення. Потрібна **парна кількість токенів**: `ключ значення ключ значення`. Числа, `true`, `false`, `null` розбираються як JSON, інші текстові значення залишаються рядками. Команда без параметрів не працює.

#### Варіант C. Готовий JSON-об'єкт

```text
set guard {"d":2,"r":4}
```

Перед надсиланням JSON перевіряється парсером RouterOS. Якщо JSON некоректний, HTTP POST не виконується — Handler повертає помилку обробки.

#### Відповідь на SET і повторне виконання

Якщо ESP32 повернув JSON, шлюз відформатує відповідь відповідно до `get=flat` або `get=raw`. Якщо відповідь порожня, отримаєте текст `POST OK (empty response)`.

Раніше під час тестування `set guard ...` сервер повернув відповідь зі змістом **`status success`**. Це підтверджує HTTP-взаємодію, але не замінює незалежного зчитування фактичного стану реле.

**Якщо відповідь на SET не надійшла, НЕ надсилайте ту саму команду вдруге навмання.** POST уже міг змінити стан. Спочатку перевірте `get guard` або локальний інтерфейс пристрою.

### 4.5. Автоматична тривога

На пристрої `guard` увімкнено фонове опитування. Коли ESP32 надсилає в JSON `"alert": true`, Smart Place формує повідомлення `ALERT guard!` з показниками та відправляє його всім довіреним номерам. Тривога зазвичай надходить **кількома SMS**, якщо звіт довгий.

**Приклад логіки подій:**

```text
До події:   alert = false    → сповіщення немає
Нова подія: alert = true     → поставлено тривогу в чергу, SMS
Триває:    alert = true     → повторення тієї ж події не планується
Скидання:  alert = false    → система готова до наступного переходу
```

Між зміною стану на ESP32 й отриманням SMS існують дві затримки: до найближчого опитування пристрою (`interval` у JSON, наприклад 60 с) та до найближчої обробки черги SMS (Scheduler кожні 20 с), **плюс робота модема/оператора**. Тому **не розраховуйте на фіксований час доставки**.

#### Що робити при реальній газовій тривозі

Дійте за правилами безпеки для вашого приміщення та типу газу; не покладайтеся лише на SMS. Не вмикайте/вимикайте електричні пристрої в потенційно вибухонебезпечному середовищі, покиньте небезпечну зону, повідомте відповідні аварійні служби. Smart Place — **допоміжний канал повідомлення**, не сертифікований захисний пристрій.

### 4.6. Що означають типові відповіді

| Повідомлення | Що це означає | Що робити |
|---|---|---|
| `Guard: get guard ...` | Підказка із локального конфіга | Далі можна надіслати GET |
| `Relay 1 = 1` | Значення, яке повернув ESP32 | Перевіряйте трактування у прошивці ESP32 |
| `alert = true` | Пристрій повідомляє про тривожний стан | Дотримуйтесь правил безпеки |
| `ERR: config JSON failed` | Помилка читання чи розбору конфігурації | Повідомте адміністратора |
| `ERR: GET failed` / `ERR: GET JSON failed` | HTTP недоступний або відповідь некоректна | Повідомте адміністратора |
| `ERR: SET parse failed` | Некоректні параметри SET | Перевірте синтаксис, **не повторюйте небезпечний POST навмання** |
| Немає SMS | Відправник не дозволений, модем/мережа недоступні або команда не розпізнана | Перевірка в журналі RouterOS |
| `guard 3/4` без `guard 4/4` | Відсутня одна з частин | Можлива помилка модема; не робіть висновок про стан реле тільки з фрагмента |

### 4.7. Обмеження та корисні правила

- Надсилайте **одну команду в одному SMS**. Довгі/складені SMS та Unicode можуть не підтримуватися модемом/RouterOS так, як звичайні короткі SMS латиницею.
- Не додавайте перед командою невидимі символи, смайлики та зайві переводи рядка.
- За замовчуванням розпізнаються лише **нижній регістр** `help/get/set` і міжнародний формат номера `+...`.
- Відправник, відсутній у непорожньому whitelist, **не отримує відповіді**.
- Нерозпізнані/пошкоджені SMS і повідомлення від `Kyivstar` не повинні викликати відповідь на службовий номер; вони можуть лишатися в Inbox для ручного аналізу.
- При перевстановленні шлюзу RAM-історія оброблених повідомлень очищується. Старі SMS в Inbox можуть бути оброблені ще раз — важливо для `set`.
- Можлива похибка/затримка датчиків ESP32; перевіряйте калібрування газового сенсора окремо.

### 4.8. Якщо ви адміністратор

```routeros
/tool sms inbox print detail
/log print where message~"SmartPlace:"
```

**Ручний запуск для діагностики (коли Scheduler вимкнений):**

```routeros

```

## Конфігурація Smart Place: JSON, SMS, REST API


### Структура файлів

Кожен IoT-пристрій має **свій** JSON-файл із точним шаблоном імені:

```text
flash/smart-place-device-<name>.json
```

`<name>` має збігатися з полем `name` усередині конфігурації. SMS Handler перевіряє допустимі символи у назві пристрою: `A–Z`, `a–z`, цифри, `_` та `-`. Пробіли й кирилиця в імені пристрою **не допускаються**.

Всі файли із цим префіксом та суфіксом `.json` потрапляють до автоматичного обходу cron. При цьому **лише `alert:true` у конфігу** вмикає фонового спостерігача для цього пристрою; `get` і `help` не залежать від цього прапорця.

### Повний приклад `guard`

```json
{
  "name": "guard",
  "ip": "192.168.12.254",
  "alert": true,
  "interval": 60,
  "help": "Guard: get guard | set guard [1,0,0,1,0]",
  "get": "flat",
  "set": "auto",
  "wrap": ""
}
```

Це **точно той формат конфігурації**, що використовується в поточному комплекті. Завантажити оригінал: [приклад JSON](downloads/smart-place-device-guard.example.json).

### Усі поля пристрою

| Поле | Тип | Обов'язковість / поведінка | Приклад |
|---|---|---|---|
| `name` | string | Для команд і перевірки відповідності імені файлу | `"guard"` |
| `ip` | string | IPv4-адреса або адресна строка пристрою для `http://<ip>/`; без порту в поточному перевіреному сценарії | `"192.168.12.254"` |
| `alert` | boolean | Якщо **точно `true`**, cron опитує пристрій; якщо `false`, фонового опитування немає | `true` |
| `interval` | number | Інтервал фонового GET у **секундах**, мінімум **20**, коли `alert=true` | `60` |
| `help` | string | Відповідь на SMS `help <name>` | `"Guard: ..."` |
| `get` | string | Підтримувані значення: `"flat"`, `"raw"` | `"flat"` |
| `set` | string | Підтримуване значення: `"auto"` | `"auto"` |
| `wrap` | string | Необов'язкова логіка вкладення **вхідного JSON-масиву** в об'єкт; порожній рядок — без вкладення | `""`, `"relays"` |

**Зауваження:** код не має повної JSON Schema-валідації на етапі інсталяції. Для нових пристроїв потрібно дотримуватися типів і перевіряти `help`, `get`, `set` і cron окремо. Некоректний `ip`, `get`, `set` або відсутні поля можуть призвести до помилки команди.

### REST API: GET

HTTP-адреса формується фіксовано:

```text
http://<ip>/
```

У поточній версії **не налаштовуються окремий path, заголовки авторизації, порт, HTTPS або параметри GET**. На ESP32 має існувати endpoint, доступний із MikroTik.

Типова відповідь `guard` — JSON-об'єкт із полями сенсорів і обов'язковою для cron ознакою тривоги:

```json
{
  "CO2": 605,
  "Gas (MQ9)": 29,
  "Humidity 1": 35.1,
  "Relay 1": 1,
  "Relay 2": 1,
  "Relay 3": 0,
  "Relay 4": 0,
  "Relay 5": 1,
  "Temperature 1": 30.6,
  "alert": false
}
```

Це **скорочений ілюстративний приклад**, а не копія всього JSON, отриманого з ESP32. Порядок і набір полів визначає пристрій.

При `get=flat` кожен ключ перетворюється на окремий рядок `ключ = значення`. Якщо значення — вкладений масив/об'єкт, воно серіалізується назад у JSON. При `get=raw` повертається сирий текст GET-відповіді.

**Для cron** у корені GET-відповіді потрібен JSON-об'єкт/структура з ключем `alert`, де значенням є **логічне `true`** або **логічне `false`**, а не рядки `"true"` чи `"false"`.

### REST API: SET — правила формування JSON

**SMS → POST:**

| SMS | HTTP body | Коментар |
|---|---|---|
| `set guard [1,0,1,0,1]` | `[1,0,1,0,1]` | Готовий масив; для `wrap:""` без змін |
| `set guard {"d":2,"r":4}` | `{"d":2,"r":4}` | Готовий JSON-об'єкт |
| `set guard d 2 r 4` | `{"d":2,"r":4}` | Пари ключ/значення; числа розпізнаються |
| `set guard enabled true` | `{"enabled":true}` | JSON boolean |
| `set guard label demo` | `{"label":"demo"}` | Не-JSON слово стає рядком |

**Лише для масиву JSON:** якщо в конфігу встановлено `"wrap":"relays"`, команда

```text
set guard [0,0,1,0,0]
```

перетвориться на:

```json
{"relays":[0,0,1,0,0]}
```

Готовий об'єкт `{"a":1}` і пари `a 1` **не загортаються** в `wrap`. Для `guard` у зафіксованій збірці `wrap` порожній, тому ESP32 отримує **голий масив**.

#### Обмеження SET-парсера

- Ключі у парах: `A–Z`, `a–z`, `0–9`, `_`, `-`.
- Параметри розділяються пробілами; складні рядки з пробілами не мають повноцінного механізму екранування у режимі пар.
- JSON-літерали `true`, `false`, `null`, числа розпізнаються як відповідні типи.
- Значення у форматі `[ ... ]` або `{ ... }` обробляються як один JSON-фрагмент від початку payload (реальна довжина SMS обмежена модемом).
- JSON надсилається у POST як `Content-Type: application/json`.
- Якщо ESP32 повертає непорожню відповідь, поточний код очікує JSON при `get=flat`; довільний текст може спричинити `ERR: SET response JSON failed` навіть якщо сама операція на пристрої виконалася.

### Політика повідомлень і номера

Файл `flash/smart-place-trusted-numbers.txt` **записується адміністратором**, не інсталятором. Приклад із замінниками номерів:

```text
+380XXXXXXXXX
+372XXXXXXXX
```

Точний синтаксис реалізації: номер починається з `+`, решта символів — цифри, довжина **9–16 символів** включно з `+`; дублікати ігноруються. Формат у SMS Inbox має **точно збігатися** з рядком whitelist, зокрема код країни. Порожні рядки під час читання пропускаються, проте не слід додавати коментарі та зайві символи. Для надійності використовуйте звичайний LF і файл без BOM.

**Стани:**

| Стан whitelist | SMS `help/get/set` | Автоматичні алерти |
|---|---|---|
| Файл **відсутній** | **Відхилені** (`DENY ALL`) | Handler не відправляє |
| Файл є, але **порожній** | **Дозволені будь-якому валідному `+...` номеру** | **Немає одержувачів** |
| Є 1+ валідних номерів | Лише точні збіги | Всім зазначеним номерам |
| Є некоректний запис / лише невалідні записи | **Відхилені** | Не надсилаються |

**Рекомендація:** перед роботою з реле ніколи не залишайте trusted list порожнім.

### Додавання другого пристрою

Приклад *схеми* (потрібен реальний REST endpoint із потрібною JSON-відповіддю; це не перевірений пристрій):

Файл: `flash/smart-place-device-pump.json`:

```json
{
  "name": "pump",
  "ip": "192.168.12.253",
  "alert": false,
  "interval": 60,
  "help": "Pump: get pump | set pump enabled true",
  "get": "flat",
  "set": "auto",
  "wrap": ""
}
```

Тут IP `192.168.12.253` — **лише приклад**; не слід припускати, що цей пристрій існує. `"alert":false` означає, що cron **не** опитуватиме його автоматично, але ручний `get pump` можливий, якщо пристрій відповідає REST JSON. Якщо ESP32 використовує інший URI, порт, автентифікацію чи форму POST, знадобиться адаптація RSC, не просто новий JSON.

### Шляхи й імена — що можна / що не можна змінювати

| Об'єкт | Зміна допустима? | Наслідок |
|---|---|---|
| `guard.json` IP / help / interval | Так, при збереженні схеми | Змінює маршрут, підказку, частоту |
| Ім'я пристрою | Так, але одночасно ім'я файлу й `name` | SMS-команди використовують нове ім'я |
| `flash/` → інший каталог | Ні без редагування RSC | Handler/cron не знайдуть конфіг |
| `lte1` → інший LTE-інтерфейс | Лише після редагування RSC і налаштування `/tool sms` | Інакше SMS не відправлятимуться |
| HTTP URI/HTTPS/API-токен | Не підтримується конфігом поточної версії | Потрібна доробка коду |
| Інтервал Scheduler | Можна, але обережно | Затримки та навантаження зміняться |
| `interval` нижче 20 с | Ні для cron поточного RSC | Помилка перевірки мінімуму |

## Безпека: хто може керувати Smart Place та що потрібно захистити


> **Критично:** Smart Place виконує керувальні дії над реле за SMS. Не використовуйте поточну систему як єдиний захист від пожежі, витоку газу чи інших небезпечних подій. Для фізично небезпечних навантажень застосовуйте незалежне апаратне захисне відключення.

### 1. Модель довіри

| Компонент | Джерело довіри | Основні ризики |
|---|---|---|
| SIM у MikroTik | Мобільна мережа й облікові дані оператора | Затримки, втрата SMS, підміна відправника, `MBIM: MEMORY_FULL` |
| SMS-відправник | Номер у міжнародному форматі | Номер телефону **не є криптографічною автентифікацією**; можливий SMS spoofing |
| Whitelist | `flash/smart-place-trusted-numbers.txt` | Випадково порожній файл відкриває керування всім коректним номерам |
| MikroTik RouterOS | Доступ адміністратора, права скриптів і Scheduler | Компрометація керування роутером, зміна RSC / налаштувань |
| ESP32 `guard` | Локальна мережа 192.168.12.0/24 у протестованій інсталяції | HTTP без TLS, відсутність автентифікації на рівні Smart Place, підміна JSON |
| GitHub Pages | Публічний репозиторій документації | Витік реальних номерів, адрес із внутрішньої інфраструктури, резервних копій |

### 2. Trusted numbers — обов'язкова конфігурація

**Файл:** `flash/smart-place-trusted-numbers.txt`. Кожен телефон на окремому рядку, початок `+`, далі тільки цифри; без пробілів та коментарів. Приклад (номер умовний):

```text
+380XXXXXXXXX
```

| Вміст файлу | Фактична поведінка поточного RSC |
|---|---|
| Файл **не існує** / не знайдений однозначно | `DENY ALL`: Handler завершується без обробки команд |
| Файл є, але він **порожній** | **Публічний режим**: `get`, `set`, `help` доступні будь-якому валідному міжнародному номеру. Автоматичні алерти нікому не розсилаються |
| Один або кілька коректних номерів | Команди виконуються тільки для них; алерти розсилаються усім у списку |
| Невалідний або некоректно відформатований непорожній список | `DENY ALL` і запис помилки в журнал |

Команди для перевірки та зміни **на власному роутері**:

```routeros
/file print detail where name="flash/smart-place-trusted-numbers.txt"
:put [/file get [find name="flash/smart-place-trusted-numbers.txt"] contents]
```

Щоб замінити список **на один свій номер** (увага: це перезаписує попередні номери):

```routeros
/file set [find name="flash/smart-place-trusted-numbers.txt"] contents="+380XXXXXXXXX"
```

Не додавайте до документації номер телефону з реальних логів. На GitHub завантажуйте лише приклад із плейсхолдерами.

### 3. Валідність команд і захист від службових SMS

SMS Handler приймає команди тільки від номерів, що відповідають його формату міжнародного номера (`+` та цифри, довжина 9–16 символів). Алфавітні відправники на кшталт `Kyivstar` не отримують відповідей. Обробляються **лише команди з маленькими латинськими літерами** `help`, `get`, `set`. Інші, пошкоджені та кириличні повідомлення поточна реалізація залишає в Inbox для перегляду.

Назва пристрою обмежена літерами ASCII, цифрами, `_` та `-`. Файли шукаються за фіксованим шаблоном `flash/smart-place-device-<name>.json`. Це обмежує спроби підставити довільний шлях у SMS.

**Чого немає:** криптографічного підпису SMS, одноразових кодів, пароля для кожної команди, антиспуфінгу на рівні оператора, розмежування `get` і `set` за окремими ролями. У whitelist всі дозволені номери мають однакові можливості.

### 4. Обмеження REST і захист локальної мережі

Поточна інтеграція звертається до `http://<ip>/` — незашифрованим **HTTP**, без токена авторизації, оскільки саме так працює випробуваний ESP32 `guard`. Не пробрасывайте ESP32 у публічний інтернет, не відкривайте порт 80 через LTE/WAN, ізолюйте IoT у довіреному LAN/VLAN і за потреби обмежуйте доступ правилами firewall. Будь-який пристрій, що дістається до цього REST API, може потенційно керувати реле незалежно від SMS whitelist.

Важливо: Smart Place не перевіряє сертифікати TLS, бо поточний URL використовує HTTP. Інша модель ESP32 може мати відмінні вимоги до безпеки — тоді адаптуйте реалізацію перед експлуатацією.

### 5. Права MikroTik і дані на flash

Два Scheduler **мусять** мати `policy=ftp,read,write,policy,test,sensitive`. На реальному Chateau / RouterOS 7.24.6 було підтверджено, що без `sensitive` автоматичний Scheduler знаходив JSON-файл, але читання `/file get ... contents` давало `nil`, що створювало `Empty device config`. Це спостережена особливість протестованої конфігурації; не видаляйте дозвіл під час редагування інсталятора.

Адміністраторський доступ до RouterOS контролюйте окремо: унікальні облікові записи, сильні паролі, оновлення безпеки, резервні копії й обмеження доступу до WinBox/SSH. **Не вмикайте віддалений доступ до RouterOS через SMS `:cmd` для роботи Smart Place:** Handler читає звичайні SMS із Inbox.

### 6. Дедуплікація та повтори

Handler веде `spHandledSms` **у RAM**: записує ключ повідомлення до списку оброблених перед спробою видалення SMS. Якщо видалення з Inbox не вдалося, після наступного запуску той самий ключ ігнорується. **Після перезавантаження/переімпорту RAM-стан скидається**; залишена в Inbox команда `set` може виконатися знову. Перед перевстановленням перевіряйте Inbox й очищуйте лише конкретні вже виконані команди.

Помилка `/tool sms send` не спричиняє автоматичного повтору — фактичне відправлення може бути неоднозначним. Це знижує ризик дублікатів, але означає, що частина відповіді або тривоги може не дійти.

### 7. Публічний GitHub Pages

**Можна публікувати:** RSC без секретів, шаблон `guard.json`, схеми, посібник та знеособлені приклади. **Не публікуйте:** реальний whitelist, SMS Inbox, дані SIM, резервні `.backup` / `.rsc` із секретами, облікові дані, приватні журнали з номерами телефонів, ключі API. GitHub Pages може бути загальнодоступним навіть при обмеженнях видимості репозиторію.

### 8. Мінімальний передексплуатаційний чеклист

- [ ] Whitelist існує, непорожній і містить лише необхідні номери.
- [ ] Роутер і ESP32 доступні тільки з довіреної мережі; немає WAN-port-forward на REST API.
- [ ] Команда `set` не керує небезпечним навантаженням без окремих апаратних захистів.
- [ ] Обидва Scheduler мають `sensitive` і виконують свої функції без `cron failure`.
- [ ] Пройдено `help`, `get`, тест із безпечним `set` і перевірка `alert=false → true → false`.
- [ ] Проблема `MBIM: MEMORY_FULL` розглядається як **відкрита** до окремого виправлення.
- [ ] Перевірено поведінку під час зникнення LTE, електроживлення й після перезавантаження.

## Діагностика та типові несправності


Документ описує **саме наявну робочу версію**, не майбутній SMS-memory fix. При виникненні помилок відключайте відповідний Scheduler і виправляйте причину поетапно; не перевстановлюйте RSC «про всяк випадок».

### 1. Швидкий алгоритм

1. Перевірити LTE та SMS: `/tool sms print`, `/tool sms inbox print detail`.
2. Перевірити RouterOS Scheduler: `/system scheduler print detail where name~"smart-place"`.
3. Перевірити останні записи: `/log print where message~"SmartPlace:"` і `/log print where topics~"script"`.
4. Перевірити JSON і HTTP через `/system script run smart-place-selftest`.
5. Окремо запустити `/system script run smart-place-cron` або `/system script run smart-place-sms-handler`, лише якщо не має бути повторно виконано стару `set`-SMS.
6. Після відновлення — вмикати окремі Scheduler, перевіряти `run-count` та **нові** логи.

#### Аварійна зупинка автоматики

```routeros
/system scheduler disable [find name="smart-place-alert-tick"]
/system scheduler disable [find name="smart-place-sms-tick"]
/system script job print detail
```

Вимкнення Scheduler не зупиняє вже розпочатий job. Якщо відповідний job дійсно завис і його потрібно зупинити, спершу перевірте його ідентичність, потім застосовуйте адресне видалення job; це **не** видалення скрипта:

```routeros
/system script job print detail
```

### 2. `Empty device config`

**Симптом:**

```text
SmartPlace: cron failure for flash/smart-place-device-guard.json: Empty device config
```

**Уже виявлена на реальному пристрої причина:** Scheduler міг знайти файл (`count=1`), але при `policy` без `sensitive` отримував `type=nil bytes=0`. Пробний Scheduler із `sensitive` отримав `type=str bytes=185`. Отже, спершу перевірте **дозволи**:

```routeros
/system scheduler print detail where name~"smart-place"
```

Очікується `policy=ftp,read,write,policy,test,sensitive` для обох. Для вже встановленої системи:

```routeros
/system scheduler set [find name="smart-place-alert-tick"] policy=ftp,read,write,policy,test,sensitive
/system scheduler set [find name="smart-place-sms-tick"] policy=ftp,read,write,policy,test,sensitive
```

Після зміни перевірте файл у тому ж контексті, де виникала помилка. Наявність файлу без права прочитати `contents` **не означає**, що JSON порожній на диску. Новий інсталятор вже має правильні Scheduler policy.

### 3. `invalid json` та `ERR: parse failed`

Причини можуть відрізнятися: неправильний файл конфігурації, відсутність дозволів під час автоматичного запуску, BOM/зайві символи, неправильно отриманий JSON від ESP32 чи помилка конкретного етапу. Лог нового Worker/Handler вказує стадію (`config JSON`, `GET JSON`, `SET response JSON`).

```routeros
/file print detail where name="flash/smart-place-device-guard.json"
:local f [/file find where name="flash/smart-place-device-guard.json"]
:local raw [/file get [:pick $f 0] contents]
:put ("bytes=" . [:len $raw])
:put ([:deserialize from=json value=$raw options=json.no-string-conversion]->"ip")
```

Для перевіреної конфігурації очікується IP `192.168.12.254` та розмір близько **185 байтів** (довжина залежить від перенесень рядків). Не замінюйте файл до підтвердження, що **саме його байти** некоректні.

### 4. HTTP GET не працює / немає датчиків

```routeros
/ping 192.168.12.254 count=4
/system script run smart-place-selftest
```

Якщо self-test отримує `code: 200` і перелік сенсорів, REST і парсинг для `guard` справні. Якщо `fetch` помиляється, перевірте IP, живлення ESP32, LAN/VLAN, firewall, HTTP root `/`, розмір відповіді та JSON. Для цього комплекту HTTP запит застосовує **RAM-файл** (`output=file dst-path=...`); на протестованому Chateau `as-value output=user` спричиняв помилку `please use 'output' option`. Не замінюйте перевірений механізм без окремого тесту.

### 5. `MBIM: MEMORY_FULL (6)`

**Статус: відомий невиправлений дефект, відкладений до другого етапу.**

Під час `get guard` модем повернув:

```text
SmartPlace: SMS part 3/4 failed ...: Can't send SMS with MBIM: MEMORY_FULL (6)
SmartPlace: reply not fully delivered
```

Це **не** свідчить про помилку ESP32. Проблема стосується SMS-сховища/поведінки модема. Підозра на накопичення повідомлень у SIM/модемі є обґрунтованою, але на цій установці джерело **ще не підтверджене AT-діагностикою**.

Безпечні діагностичні команди, що **нічого не видаляють**:

```routeros
/tool sms print
/tool sms inbox print detail
/interface lte at-chat lte1 input="AT+CPMS?" wait=yes
```

`AT+CPMS?` залежить від можливостей модема й може бути недоступною через MBIM. Не виконуйте навмання команди масового видалення SMS (`AT+CMGD=1,4` і подібні): вони можуть знищити потрібні вхідні повідомлення. **Стадія 2** — окреме розслідування, рішення, контрольні тести й окремий випуск RSC. До цього моменту аварійні SMS не можна вважати гарантованими.

### 6. Прийшли не всі частини `get guard`

Handler розділяє довгу відповідь на **окремі** SMS (по **64 символи даних** максимум на частину; до **8 частин**), додаючи заголовок `<device> i/n:` та паузу **3 с** між відправленнями. Це **не** справжні concatenated SMS; частини можуть прийти не за порядком або загубитися. Пошукайте:

```routeros
/log print where message~"SmartPlace: SMS part"
/log print where message~"SmartPlace: reply not fully delivered"
```

Повтор `get` — безпечне читання, але після `MBIM: MEMORY_FULL` без відновлення SMS-пам'яті він не вирішує проблему. Автоматичні повторні відправлення навмисно не ввімкнені.

### 7. На `get` прийшов попередній `help`

Можливі дві причини: затримка доставки старої SMS з боку мобільного оператора або повторна обробка повідомлення, яке залишилося в Inbox після невдалого видалення. У поточному Handler є RAM-дедуплікація `spHandledSms` за ID і timestamp, але вона **скидається після reboot або імпорту**.

```routeros
/tool sms inbox print detail
/log print where message~"inbox delete failed"
```

Не видаляйте всі повідомлення; прибирайте лише точно ідентифіковані старі команди, особливо `set`.

### 8. Висить `help guard` / SMS Handler

Обробник SMS ізольовано від cron; `help` більше не запускає фонове REST-опитування. Проте виклик `/tool sms send` може затримуватись через LTE. Потрібно відрізняти **реально активний** job від довгої доставки SMS:

```routeros
/system script job print detail
/tool sms print
/log print where topics~"script"
```

Число `1`, яке друкується під час ручного виклику скрипта, саме по собі **не є** статусом зависання — це може бути результат команди `print count-only` усередині скрипта.

### 9. `cron failure` після встановлення

Спершу звірте **час** повідомлення з останнім імпортом. Старі `cron failure` залишаються в історії журналу; якщо `run-count` зростає й **нових** `script,warning` немає, це позитивний результат. Проте `run-count` означає тільки факт запуску Scheduler, а не гарантований HTTP 200 у кожному циклі: для `guard` частота Scheduler 20 с, а опитування самого пристрою — раз на 60 с.

### 10. Whitelist: нічого не відповідає

```routeros
/file print detail where name="flash/smart-place-trusted-numbers.txt"
:put [/file get [find name="flash/smart-place-trusted-numbers.txt"] contents]
```

Відсутній чи невалідний файл: Handler блокує всю обробку. Порожній — небезпечний режим доступу з будь-якого номера. Якщо скрипт виконується з Scheduler, перевірте `sensitive`. Переконайтеся, що номер у whitelist точно збігається з `phone` із Inbox, включно з кодом країни.

### 11. Службові SMS, `Kyivstar`, `????`

Сучасний Handler не відповідає алфавітним відправникам й ігнорує команди, що не починаються з допустимого `get`, `set`, `help`. Для кирилиці можливі обмеження кодування SMS і відображення `????`. Це не означає, що можна безпечно ігнорувати всі системні повідомлення оператора: перевіряйте Inbox вручну та робіть адресне видалення.

### 12. Постійні проблеми після імпорту

Перевірте, що імпорт створив **три скрипти** (`smart-place-selftest`, `smart-place-sms-handler`, `smart-place-cron`) і **два Scheduler** (`smart-place-sms-tick`, `smart-place-alert-tick`), а старих Worker/Scheduler немає. Інсталятор не змінює `guard.json` та trusted numbers, зате **скидає RAM-стан**, зокрема дедуплікацію й чергу. Імпорт не є засобом очищення SMS-пам'яті.

## Експлуатація та обслуговування Smart Place


Цей розділ — робочий регламент після первинного встановлення. Для повної інсталяції на новому роутері див. [розділ 3](#installation), а для кінцевого користувача — [розділ 4](#usage).

### 1. Що має працювати постійно

- `/tool sms`: `receive-enabled=yes`, `port=lte1`, стан `running` за підтримки модема.
- `smart-place-sms-tick`: Scheduler кожні 20 с запускає `smart-place-sms-handler`, обробляє вхідні команди та чергу алертів.
- `smart-place-alert-tick`: Scheduler кожні 20 с запускає `smart-place-cron`, що сканує `flash/smart-place-device-*.json` і опитує пристрої за їх власним `interval` (для `guard` — 60 с).
- На конфігах `guard` з `"alert": true` і REST-відповіддю `"alert": true` cron ставить тривогу в RAM-чергу, а Handler розсилає її на номери із whitelist.

Не плутайте **значення `alert` в JSON-конфігурації** (чи включено моніторинг) і **значення `alert` у відповіді ESP32** (чи існує тривога прямо зараз).

### 2. Швидкі команди оператора

| Дія | Команда RouterOS |
|---|---|
| Перевірити SMS | `/tool sms print` |
| Подивитися Inbox | `/tool sms inbox print detail` |
| Перевірити Scheduler | `/system scheduler print detail where name~"smart-place"` |
| Перевірити jobs | `/system script job print detail` |
| Перевірити помилки Smart Place | `/log print where message~"SmartPlace:"` |
| Self-test (без POST/SMS) | `/system script run smart-place-selftest` |
| Ручне опитування | `/system script run smart-place-cron` |
| Обробити Inbox вручну | `/system script run smart-place-sms-handler` |

#### Вмикання / вимикання кожного процесу

```routeros
/system scheduler disable [find name="smart-place-sms-tick"]
/system scheduler disable [find name="smart-place-alert-tick"]
```

```routeros
/system scheduler enable [find name="smart-place-alert-tick"]
/system scheduler enable [find name="smart-place-sms-tick"]
```

Перша команда вмикання відновлює опитування; друга — обробку SMS і доставку черги. **Якщо SMS Handler вимкнений, алерти не надсилатимуться**, навіть якщо cron справно їх виявляє.

### 3. Порядок безпечного оновлення

1. Зафіксуйте дату, версію RouterOS, файли та поточний стан; переконайтеся, що немає активної керувальної команди `set`.
2. Вимкніть **обидва** Scheduler. Перевірте `/system script job print detail`: інсталятор відмовляється міняти скрипт, поки той виконується.
3. Перевірте Inbox і вручну визначте вже оброблені повідомлення. Через скидання `spHandledSms` на повторному імпорті команда `set`, що залишилась у Inbox, може повторитися. **Не очищайте все одним викликом.**
4. Збережіть окремо `flash/smart-place-device-*.json`, `flash/smart-place-trusted-numbers.txt` (лише в захищеному місці) та поточний RSC. **Увага:** звичайний `/export` може не зберегти файли `flash/` як вміст.
5. Замініть RSC у WinBox → Files, виконайте:

   ```routeros
   /import file-name=smart-place-install.rsc verbose=yes dry-run
   /import file-name=smart-place-install.rsc
   ```

6. Перевірте права Scheduler (`sensitive`), запустіть self-test, cron і перевірку `help`/`get`. **Інсталятор завжди залишає обидва Scheduler вимкненими**, незалежно від попереднього стану.
7. Увімкніть спочатку alert-tick, потім sms-tick; відстежуйте свіжі warnings і фактичну доставку SMS.
8. Зафіксуйте результат у журналі змін. Не вважайте тест `run-count` підтвердженням доставки тривоги.

**Ця документаційна збірка не змінює RSC** відносно зафіксованого робочого стану; проблема SMS-пам'яті не виправлена.

### 4. Резервна копія й відновлення

Мінімальний комплект відновлення: перевірений `smart-place-install.rsc`, JSON усіх пристроїв, непорожній whitelist, відомості про `lte1`, локальні IP/VLAN та спосіб доступу до роутера. Рекомендовано зберігати також контрольні версії/хеші файлів і коротку таблицю тестів.

```routeros
/system backup save name=smart-place-before-change
/export file=smart-place-config-before-change
```

Завантажуйте резервні файли **в захищене сховище**, враховуючи обмежену пам'ять Chateau. Не публікуйте їх. Відновлення іншої моделі MikroTik з бінарного backup може бути несумісним; для міграції окремо відтворюйте мережу, LTE й файли.

#### Після перезавантаження

Перевірте `status: running`, обидва Scheduler, файли `flash/`, доступ до ESP32 та актуальність телефонних номерів. **Глобальні стани в RAM (`spPriorAlert`, `spLastCheck`, `spPendingAlerts`, `spHandledSms`) не зберігаються**, тому вже активна тривога може бути поставлена в чергу повторно, а залишена в Inbox команда `set` — оброблена повторно.

### 5. Щоденний / щотижневий огляд

| Періодичність | Дія | Критерій |
|---|---|---|
| Після будь-якого імпорту | Перевірити `disabled`, права Scheduler, self-test | Очікувана структура й HTTP 200 |
| Раз на день за можливості | Переглянути SmartPlace warnings, рівень доступності LTE | Немає нових `cron failure`, `MEMORY_FULL` |
| Раз на тиждень | Перевірити Inbox та використання SMS-сховища | Немає застряглих/дубльованих команд |
| Після зміни ESP32 | Запустити GET і безпечний тест SET | Формат відповіді й керування відповідають контракту |
| Після збоїв електроживлення | Перевірити SMS та стан тривоги | Відомий стан після reboot |
| Після зміни номерів | Перевірити whitelist | Лише дійсні одержувачі, не порожній |

### 6. Тестування тривоги без небезпечних експериментів

Раніше на реальному датчику газу було підтверджено тривогу, отримання 4/4 SMS та повернення `alert=false`. Для подальших регресійних тестів **не випускайте горючий газ у приміщення**. Використовуйте передбачений ESP32 тестовий механізм / програмну імітацію, якщо такий буде реалізований. Перевіряйте послідовність `false → true → false`, а потім нову тривогу після скидання. Сам RSC не містить команди примусової імітації `alert=true`.

### 7. Обмеження RAM-черги алертів

- Черга `spPendingAlerts` зберігається лише в RAM та **скидається** під час інсталяції/перезавантаження.
- Handler забирає поточний snapshot черги та **очищає її перед SMS-розсилкою**. Якщо надсилання завершується помилкою, такий запис **не повертається автоматично** в чергу.
- Для `guard` cron запам'ятовує стан `true` після постановки в чергу: якщо SMS не дійшло, він **не створюватиме повторний алерт**, поки відповідь ESP32 знову не стане `false`, а потім `true`.
- Один ключ пристрою в черзі зберігає лише останній підготовлений звіт; це не гарантійна журналювана черга.

Тому канал SMS **потребує другого етапу підвищення надійності** (зокрема проблеми `MBIM: MEMORY_FULL`), перш ніж використовувати його як єдине аварійне сповіщення.

### 8. Контрольний чеклист введення в роботу

- [ ] LTE і SMS працюють; номер SIM відомий користувачам.
- [ ] `flash/` містить всі JSON і **непорожній** whitelist.
- [ ] Є резервний RSC та захищений backup файлів.
- [ ] Self-test показує HTTP 200 та очікувані дані.
- [ ] SMS `help` і `get` надходять без ручного запуску Handler.
- [ ] Тестовий `set` не викликав небезпечної зміни обладнання.
- [ ] Обидва Scheduler мають `sensitive`, `run-count` збільшується, **нові** warnings відсутні.
- [ ] Є безпечний план перевірки алертів і план дій при втраті LTE/SMS.
- [ ] `MBIM: MEMORY_FULL` позначено як невирішений ризик.

**Далі:** [Діагностика](#troubleshooting) · [Безпека](#security).

## Технічний довідник для інтегратора та розробника


> **Scope:** наведено опис саме `downloads/smart-place-install.rsc` — зафіксованої збірки RouterOS 7.24.6. Другий етап з усунення SMS-memory bug поки **не реалізований**. Зміна скриптів потребує регресійного тестування на MikroTik.

### 1. Склад RSC і межі відповідальності

Інсталятор додає **три** RouterOS скрипти:

| Скрипт | Відповідальність | Що навмисно не робить |
|---|---|---|
| `smart-place-selftest` | Читає `guard.json`, перевіряє шляхи завантаження, виконує HTTP GET, JSON parser і сухий тест SET body | Не виконує POST і не надсилає SMS |
| `smart-place-sms-handler` | Читає Inbox, перевіряє відправника/whitelist, маршрутизує HELP/GET/SET, виконує REST, формує SMS і відправляє чергу алертів | Не робить циклічне опитування ESP32 |
| `smart-place-cron` | Знаходить `flash/smart-place-device-*.json`, відстежує час опитування та стан `alert`, додає тривожний звіт у RAM | Не звертається до LTE-модема для надсилання SMS |

І **два** Scheduler із інтервалом 20 с, обидва **disabled=yes** після кожного імпорту:

```routeros
/system scheduler add name="smart-place-sms-tick" interval=20s start-time=00:00:00 on-event="/system script run smart-place-sms-handler" disabled=yes policy=ftp,read,write,test,policy,sensitive
/system scheduler add name="smart-place-alert-tick" interval=20s start-time=00:00:00 on-event="/system script run smart-place-cron" disabled=yes policy=ftp,read,write,test,policy,sensitive
```

Згідно з тестом на реальному Chateau дозвіл **`sensitive`** потрібен для читання `/file ... contents` зі Scheduler, інакше отримували `nil` та `Empty device config`. Самі скрипти додаються з `ftp,read,write,test,policy`. Зміна прав — свідоме функціональне рішення; забезпечте захист адміністраторського доступу до роутера.

### 2. Структура файлової системи

```text
flash/
├── smart-place-device-guard.json      # постійний конфіг IoT, приклад guard
├── smart-place-device-<name>.json    # довільна кількість інших конфігів
└── smart-place-trusted-numbers.txt   # постійний whitelist телефонів

(root Files у RAM, не flash/)
├── smart-place-selftest-http.txt     # тимчасовий результат GET
├── smart-place-sms-http.txt          # тимчасовий GET / POST
└── smart-place-cron-http.txt         # тимчасовий GET моніторингу
```

Використовується `fetch output=file dst-path=<temp>` без `as-value` та без `keep-result`: це перевірений спосіб для протестованого Chateau. Скрипти прибирають тимчасові файли після використання та на гілках обробки помилок. Якщо job примусово перерваний, тимчасовий файл може залишитися; на наступному запуску конкретний скрипт видаляє свій старий файл.

### 3. Глобальні дані в RAM

| Ім'я | Тип / ключ | Хто змінює | Призначення |
|---|---|---|---|
| `spLastCheck` | map: `device → timestamp` | cron | Коли пристрій останній раз опитано |
| `spPriorAlert` | map: `device → bool` | cron | Попередній відомий стан тривоги, для детекції переходу `false → true` |
| `spPendingAlerts` | map: `device → formatted report` | cron записує; handler споживає | Одноразова RAM-черга сповіщень |
| `spHandledSms` | map: `msgId-timestamp → true` | handler | Захист від повторної обробки повідомлень, які не вдалося вилучити з Inbox |

Усі ці дані скидаються під час імпорту RSC і втрачаються після перезавантаження. **Немає** транзакційності та гарантованої персистентної доставки алертів.

### 4. Пайплайн вхідної SMS

1. Scheduler `smart-place-sms-tick` викликає Handler.
2. Захист від перекриття перевіряє кількість job із поточним іменем скрипта; за наявності іншого job запуск пропускається.
3. Завантажується trusted numbers. Відсутній / невалідний файл → `DENY ALL`; **порожній** файл → `publicAccess=true`, але відсутні номери для автоматичних алертів.
4. Для кожної SMS: перевіряється `msgId + timestamp` у `spHandledSms`.
5. Перевіряється формат відправника `+` + цифри. Алфавітні відправники не обробляються.
6. За першим пробілом береться команда; лише `get`, `set`, `help` нижнім регістром підтримуються.
7. Якщо номер дозволено, розбирається назва пристрою та шлях його JSON; потім `:deserialize from=json ... options=json.no-string-conversion`.
8. `help` повертає рядок `help` із конфіга. `get` робить HTTP GET `/`. `set` парсить payload і робить HTTP POST `/`.
9. `formatResponse` для `get=flat` перетворює верхній рівень JSON в `key = value`; для `raw` повертає тіло без змін.
10. `sendPages` ділить текст на частини по 64 символи даних, максимум 8 частин, із 3-секундними паузами. При помилці логуються номер невдалої частини та помилка модема, але повтору немає.
11. `spHandledSms` оновлюється **до** спроби видалити SMS з Inbox, щоб при помилці видалення наступний tick не виконав знову POST.
12. Після Inbox Handler забирає snapshot `spPendingAlerts`, очищає глобальну чергу і відправляє кожен звіт усім довіреним телефонам.

#### Важлива межа: `spHandledSms`

Ключ заснований на ID повідомлення RouterOS та його `timestamp`, не на криптографічному ідентифікаторі. Журнал RAM не обмежений життєвим циклом у межах сесії RouterOS, тому при довготривалому невдалому видаленні Inbox може накопичувати записи; після рестарту він повністю очищається. Немає повноцінної дедуплікації на диску.

### 5. GET/SET — контракти і парсер

#### GET

```http
GET http://192.168.12.254/
```

Очікується коректний JSON; форматовані рядки для `get=flat` мають вигляд `CO2 = 605`, `Relay 1 = 1`, `alert = false`. Значення верхнього рівня — складні масиви/об'єкти — серіалізуються в JSON рядок. Для нового пристрою перевіряйте розмір відповіді та тривалість HTTP.

#### SET

```text
set guard [0,0,0,0,0]
set guard d 2 r 4
set guard {"d":2,"r":4}
```

Режим `set=auto`: якщо payload починається з `[` або `{`, він парситься як JSON array/object; якщо ні — розбивається на **пари** `ключ значення` за пробілами, значення, схоже на JSON (`2`, `true`, `null`), серіалізується як відповідний JSON тип, інакше лишається рядком. Ключі допускають ASCII літери, цифри, `_`, `-`. Для масиву з непорожнім `wrap` він перетворюється в об'єкт із названим полем; для `guard` `wrap=""`, тобто відправляється сам масив. Відправка — `POST /` із `Content-Type:application/json`.

> Поточний код не перевіряє діапазони параметрів конкретного ESP32; це відповідальність firmware. Використовуйте апаратні міжблокування для реле, що керують небезпечним обладнанням.

### 6. Пайплайн автоматичного алерту

1. Scheduler `smart-place-alert-tick` викликає cron кожні 20 с.
2. Cron сканує лише файли із префіксом `flash/smart-place-device-` і суфіксом `.json`, перевіряє збіг `name` з іменем файлу.
3. Якщо в конфігу `alert=true`, перевіряє `interval` (число, **не менше 20 с**). Якщо із попереднього GET часу менше `interval`, пропускає пристрій.
4. У разі `due=true` робить HTTP GET кореневого URL і розбирає JSON.
5. Якщо `status.alert=true` і `spPriorAlert[device] != true`, форматує звіт, записує його в `spPendingAlerts[device]`, встановлює `spPriorAlert[device]=true` і пише `SmartPlace: queued alert <device>`.
6. При `status.alert != true` встановлює `spPriorAlert[device]=false`.
7. Handler при наступному запуску забирає підготовлений звіт і **лише він** звертається до `/tool sms send` для кожного номера у whitelist.

Діаграма станів: [Mermaid-схема](diagrams/alert-state.mmd) · [Розділ архітектури](#architecture).

#### Семантика перезапуску / фонових збоїв

- На чистому RAM-стані вже активне `status.alert=true` може створити нове повідомлення. Це не гарантія «рівно один алерт на фізичну подію» після reboot.
- При помилці HTTP `spLastCheck` уже може бути оновлений до початку GET; повторна спроба буде після наступного `interval`, а не миттєво.
- Якщо алерт не відправлено, Handler не повертає його в `spPendingAlerts`. Поки `status.alert` залишається true, cron не створює новий алерт.
- Якщо whitelist порожній, cron усе одно може ставити алерт у RAM, але Handler не має адресатів і очищає чергу при споживанні. Це не є каналом доставки.

### 7. Інсталятор: ідемпотентність і побічні ефекти

Перед заміною компонентів інсталятор вимикає відомі Scheduler і відмовляється перевстановлювати скрипти, доки відповідні jobs ще активні. Потім видаляє **тільки** власні старі Scheduler / скрипти (включно з legacy `smart-place-worker`, `smart-place-tick` та `check-sms-inbox`) і створює актуальні. **Не чіпає** `flash/smart-place-device-*.json` і `flash/smart-place-trusted-numbers.txt`.

| Після імпорту | Стан |
|---|---|
| `smart-place-selftest`, `smart-place-sms-handler`, `smart-place-cron` | Є, оновлені |
| `smart-place-sms-tick`, `smart-place-alert-tick` | Є, `disabled=yes`, `policy` з `sensitive` |
| Конфіги `flash/` | Без змін |
| Глобальні RAM-змінні | Скинуті |
| Старі активні завдання | Установка має зупинитись при виявленні активного job, проте Scheduler вже були вимкнені |
| Застарілі SMS у Inbox | **Не видалені автоматично** |

Наслідок: повторний імпорт після неуспішного SMS-видалення може повторно виконати старий `set` — перевіряйте Inbox **до** імпорту.

### 8. Технічні обмеження й борги

- **Відкритий дефект:** `MBIM: MEMORY_FULL (6)` (невизначено, SIM чи модемне сховище); відповідні розділи [діагностики](#troubleshooting#mbim-memory_full-6) та [експлуатації](#operations).
- **Немає доставки exactly-once:** асинхронність SMS і скидання RAM не дають такої гарантії.
- **Немає TTL/підтвердження на чергу:** якщо відправка SMS не вдалася, тривога втрачається з RAM-черги.
- **HTTP без TLS/auth:** локальна LAN-зона довіри, не публікувати порт ESP32.
- **Один код усіх об'єктів:** налаштування `get=flat|raw`, `set=auto`; невідомі режими викликають помилку.
- **Глобальна телеметрія недостатня:** нормальний GET із cron не пише окремий `200 OK` у лог; `run-count` сам по собі цього не гарантує.
- **Довжина SMS:** максимум 8 частин по 64 символи даних, надлишок обрізається (`[TRUNCATED]`). Не придатне для великих JSON.
- **Дублікати й фонова черга:** глобальні змінні змінюються двома процесами. Запуски розведені функціонально, але у RAM немає транзакційного mutex.
- **Розширення:** потрібна валідація IP, часова межа HTTP, контроль обсягу журналів, додаткові тести на кожен новий пристрій.

### 9. Протокол тестування зміни коду

1. Зберегти контрольну копію RSC, конфігів і whitelist (не публікувати особисті номери).
2. Вимкнути обидва Scheduler і перевірити jobs.
3. Внести одну групу змін, виконати статичну перевірку RSC та `/import ... dry-run` на тестовій системі.
4. Self-test: JSON, HTTP 200, відсутність POST/SMS.
5. Handler вручну: нова SMS `help guard`, далі `get guard`; перевірити повну кількість SMS.
6. Cron вручну: `alert=false`, HTTP 200, відсутність warnings.
7. Обидва Scheduler: `sensitive`, збільшення `run-count`, відсутність нових помилок.
8. Тест алерту **лише безпечним способом**, із переходом `false→true→false` та підтвердженням одержувачів.
9. Перевірити поведінку при reboot, пропажі LTE й заповненні SMS-сховища.
10. Оновити **весь комплект документації, README, діаграми та ZIP** у тому ж релізі.

**Далі:** [Завантажити інсталятор](downloads/smart-place-install.rsc) · [Повні JSON-правила](#configuration).

## GitHub Pages: публікація документації з темою Architect


Цей архів — **вже готовий Jekyll-сайт**. Його можна розпакувати в корінь GitHub-репозиторію. Вибрана офіційна тема GitHub Pages **Architect v0.2.0**.

### 1. Що всередині ZIP

```text
_config.yml                  # Jekyll / remote_theme
index.md                     # Головна
README.md                    # Інструкція для репозиторію
_includes/nav.md             # Єдине меню сторінок
assets/architecture.svg      # Готова SVG-діаграма для браузера
diagrams/*.mmd               # Вихідні Mermaid-схеми
diagrams/components.puml      # UML / PlantUML-джерело
overview.md                   # Розділ 1
architecture.md               # Розділ 2
installation.md               # Розділ 3
usage.md                      # Розділ 4
configuration.md              # Довідник REST і JSON
security.md                   # Безпека
troubleshooting.md            # Діагностика
operations.md                 # Експлуатація
developer.md                  # Для розробників
github-pages.md               # Ця інструкція
downloads/                   # Зафіксований робочий RSC та приклади
```

### 2. Тема Architect — точна конфігурація

В `_config.yml` є:

```yaml
remote_theme: pages-themes/architect@v0.2.0
plugins:
  - jekyll-remote-theme
```

Це синтаксис, рекомендований авторами теми [pages-themes/architect](https://github.com/pages-themes/architect). **Не використовуйте `.nojekyll`**: тоді Markdown не проходитиме Jekyll-збірку, а `remote_theme` не застосовується.

Додаткові змінні: `title`, `description`, `lang`, `show_downloads`, `baseurl`, `url`. Усі сторінки використовують `layout: default` та окремий `permalink`, тож навігація має зручні адреси `/overview/`, `/architecture/`, тощо.

### 3. Створіть репозиторій на GitHub

1. Відкрийте [GitHub](https://github.com) і створіть репозиторій, наприклад `smart-place-docs`.
2. Розпакуйте ZIP і завантажте **весь вміст папки** `smart-place-github-pages` у корінь репозиторію — не додаткову вкладену папку. `_config.yml` і `index.md` мають опинитися на верхньому рівні.
3. Перевірте, що в `downloads/` лежить лише шаблон конфігурації та RSC, **немає реальних номерів телефонів**, `backup`, SIM-даних або журналів з приватними даними.
4. Commit / push у вибрану гілку, наприклад `main`.

### 4. Налаштуйте адресу сайту — `baseurl`

У ZIP за замовчуванням:

```yaml
baseurl: ""
url: ""
```

Для репозиторію виду **`USERNAME.github.io`** (user/org site) зазвичай залишають `baseurl: ""`; сайт матиме адресу `https://USERNAME.github.io/`.

Для звичайного репозиторію **`smart-place-docs`** (project site) задайте:

```yaml
url: "https://USERNAME.github.io"
baseurl: "/smart-place-docs"
```

Змініть `USERNAME` на ваш GitHub login, а `smart-place-docs` — на **точну назву репозиторію**. Посилання між розділами в цьому комплекті зроблені відносно шляху сторінок; якщо надалі змінюєте структуру permalink чи ставите сайт у підпапку, перевірте навігацію. Для нестандартного домену потрібна окрема конфігурація URL/публікації.

### 5. Увімкніть Pages

У GitHub відкрийте **Settings → Pages**. У **Build and deployment → Source** оберіть **Deploy from a branch**. Далі задайте Branch `main` та Folder `/ (root)`, натисніть **Save**. GitHub почне публікацію після commit; у Settings → Pages буде URL сайту. Для розширеного custom build можна використовувати Actions, але для цієї Jekyll-структури зазвичай достатньо Branch source.

Офіційна довідка: [Configuring a publishing source](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site), [Adding a theme with Jekyll](https://docs.github.com/en/pages/setting-up-a-github-pages-site-with-jekyll/adding-a-theme-to-your-github-pages-site-using-jekyll).

### 6. Перевірка після публікації

- [ ] Головна відкривається з оформленням **Architect**.
- [ ] Видно діаграму `assets/architecture.svg`.
- [ ] Працюють переходи до чотирьох головних розділів і довідників.
- [ ] Кожен `[Завантажити ...]` відкриває точний файл у `downloads/`.
- [ ] Код RouterOS і блоки JSON відображаються моноширинно.
- [ ] У репозиторії **немає** приватного whitelist та знімків SMS Inbox.
- [ ] Перевірено сайт зі смартфона: заголовки, довгі таблиці, великі code blocks.

Якщо Jekyll пише `Remote Theme ... not found`, перевірте написання `remote_theme` та `plugins` і журнал Pages build. Якщо сторінка **без стилю**, перевірте, що збірку не вимкнули `.nojekyll` і що `_config.yml` на рівні `index.md`. Якщо сторінки відкриваються, а посилання ведуть не туди — перевірте `baseurl`, ім'я репозиторію та `permalink`.

### 7. Як підтримувати документацію актуальною

Внесення змін до RSC і зміна API ESP32 — це окремий реліз. У такому разі оновлюйте одночасно: `downloads/smart-place-install.rsc`, `downloads/smart-place.zip`, JSON-приклади, розділи `configuration`, `architecture`, `installation`, `usage`, а також `README.md`. У GitHub commit вказуйте, які зміни **перевірені на MikroTik**, а які лише написані. **Поточний реліз — документація без другого етапу фіксу `MEMORY_FULL`.**
